# 领域类图初稿审查清单

本文件是设计核对材料，不是实验报告正文。依据实验一 requirements.md（lab1-final）、report.pdf、chat.txt 的相关业务规则，以及当前组件图源码。最终需求清单优先于 chat.txt 中的 AI 初稿与拟稿说明。类图描述领域数据，不将组件直接改成类，不包括控制器、仓储、数据库类或支付、物流等范围外功能。

## 主要关联与多重性

图中关联标签的两侧角色，依次属于下表左、右类。多重性表示一端对象能够关联多少个另一端对象。

| 左类及角色 | 右类及角色 | 含义 |
|---|---|---|
| User.seller：1 | Product.listedProducts：0..* | 每件商品一位卖家；一个用户可发布多件商品 |
| User.buyer：1 | Reservation.purchases：0..* | 每条预约一位买家；一个用户可有多条预约 |
| Product.product：1 | Reservation.reservations：0..* | 每条预约对应一件商品；商品保留多条历史预约 |
| Product.reviewedProduct：1 | ReviewRecord.reviews：0..* | 每条审核记录对应一件商品，重审增加记录 |
| User.reviewer：1 | ReviewRecord.reviewActions：0..* | 每条已作决定的审核记录对应一位管理员 |
| Reservation.reservation：1 | TerminationRequest.terminationRequests：0..* | 每个申请归属一条预约，可保留多次历史申请 |
| User.applicant：1 | TerminationRequest.applications：0..* | 每个申请恰有一个发起用户 |
| User.handler：0..1 | TerminationRequest.handledApplications：0..* | 未处理或系统关闭时可无管理员；人工决定由一位管理员负责 |
| Product.violatingProduct：1 | ViolationRecord.violationRecords：0..* | 每条违规处置针对一件商品，保留多次历史 |
| User.operator：1 | ViolationRecord.violationActions：0..* | 每次违规处置由一位管理员执行 |
| Reservation.terminatedReservation：0..1 | ViolationRecord.terminationViolation：0..1 | 每次处置至多终止一条有效预约；一条预约至多被一次违规处置终止 |
| User.recipient：1 | Notification.notifications：0..* | 每条通知仅对应一位接收人 |
| User.actor：0..1 | OperationLog.logs：0..* | 用户操作关联用户；系统自动操作可以没有用户 |

## 根据需求推断的建模选择

1. **身份统一使用 User。** accountType 仅区分普通用户与管理员；买家、卖家由 seller、buyer 关联表达。同一普通用户可同时拥有两类关联，不创建 Buyer/Seller 子类。预约卖家沿 product.seller 推导，避免额外关联引入不一致。（REQ-001、002）
2. **ReviewRecord 仅表示已经作出通过/驳回决定的审核。** 待审核由商品状态表达；送审、撤回在操作日志中留痕；reviewedVersion 指明审核的商品版本。若需要查看每次送审的完整内容，可后续补充送审批次或内容快照，本稿未声称已有完整版本存档。（REQ-004、005、018）
3. **普通终止处理结果内嵌在 TerminationRequest。** 保存双方意见、管理员、原因及时间，暂不独立建立 TerminationRecord。违规终止单设 ViolationRecord，无需普通终止申请或双方同意。（REQ-008、019）
4. **Notification 同时承载待发送记录与站内通知。** 用投递状态、发送和已读时间表达生命周期。双方通知生成两条接收人不同的记录，建议 `(eventKey, recipient)` 唯一，重试不重复生成通知。状态名称、eventKey 是设计推断。（REQ-020；INT-01-L058）
5. **通知和日志使用“对象类型＋编号”引用业务对象。** 每条通知有一个主对象；日志失败时允许目标编号为空，或保留未能解析为现存对象的输入编号。这是逻辑引用，不代表数据库已提供多态外键；实现时须校验合法类型和对象范围，不能凭编号授权。（REQ-022、030）
6. **违规处置记录的预约关联只表示被此次处置终止的预约。** 没有有效预约或商品已经完成时，此关联为空；已完成交易通过 Product 的历史预约关系追溯，不倒改完成状态。（REQ-008、015）
7. **分类与图片先建为属性。** category 为可选分类值，imageRefs 为有序图片引用集合；需求未要求分类维护、层级分类及独立图片生命周期，故未增加 Category、ProductImage 类。（REQ-003、021）
8. **预约快照内嵌为不可修改属性。** 包括标题、价格和创建时商品版本；商品与预约各有独立 version。publicHidden 独立于商品状态，用于表达已完成商品事后违规隐藏。预约终止申请状态枚举、预约版本、字段名称均为初稿设计选择。（REQ-006、008、011、018）
9. **本稿不展开预约请求处理记录。** Reservation.requestId 表示创建预约的原始请求，不足以单独表达失败请求、新标识返回既有预约等所有幂等结果；组件图持久化中的“请求结果”仍需在接口/存储设计中落实，不能仅凭预约表上的唯一索引宣称完成 REQ-017。

## 必须保留的需求约束

- 商品到预约保持 `1—0..*` 历史关联，另加约束：**同一时刻最多一条有效预约**；有效状态仅为“待卖家确认、已确认”。不得将历史多重性改成 0..1。（REQ-016、029）
- `Reservation.buyer != Reservation.product.seller`；双方均为普通账号。审核人、违规处置人和人工终止处理人须为管理员；管理员不得代买家完成交易。（REQ-002）
- 商品状态为八项 ProductStatus，预约状态为七项 ReservationStatus。商品“已预约”须对应一条“待卖家确认”预约；商品“已确认”对应一条“已确认”预约；其他商品状态不能有有效预约。预约终态不能复活，完成商品不能复售。（REQ-015）
- 每条预约同一时刻最多一个待处理终止申请。申请人为交易参与者，普通批准须核实双方同意；买家先完成时关闭待处理申请，之后不能再终止。（REQ-014、019、029）
- 未完成商品违规处置：商品转违规下架、有效预约转已终止；已完成商品仅追加记录并隐藏，商品及预约完成状态不变。（REQ-008）
- 新预约创建前校验商品当前已发布、无有效预约、版本及价格与用户确认一致；价格快照不随商品修改变化。商品与预约状态、处理记录、成功日志、待发送通知整体提交，任一必要写入失败回滚；实际通知在提交后发送。（REQ-011、018、020）
- 同一用户的请求标识唯一定位一次处理：同标识同内容重放原结果，同标识不同内容拒绝。该约束属于请求处理记录，不等于每次重试都新增 Reservation。（REQ-017）
- 草稿可缺字段，因此主要业务字段标为 [0..1]；送审前字段齐全、图片 1–5 张、标题≤100字、描述≤2000字，价格大于0且≤100000元、至多两位小数。（REQ-003）
- 日志 actor 与 systemActor 二选一；失败日志在业务回滚后单独保留，密码、密码哈希和完整联系方式不进入日志。日志只追加、至少保留180天且课程结束前不清理。（REQ-022、025）
- 联系方式仅向满足关联、状态及权限条件的参与者和有处理职责的管理员开放；实体存在 contactInfo 属性不表示所有接口都可返回它。（REQ-030）
- 用户名与各实体编号唯一；历史预约、审核、违规、申请与快照保留，关联均未使用暗示级联销毁的组合关系。（REQ-029；INT-02-L024）
