# 提交预约序列图初稿核对

依据：实验一最终 requirements.md、report.pdf、chat.txt 相关规则，及当前类图、商品状态图、预约状态图。本文件为设计核对材料，不是实验报告正文。

## 分支与需求映射

| 情况 | 处理 | 需求 |
|---|---|---|
| 同买家、同 requestId、同内容 | 返回首次 resultCode/resultReason，若关联预约则读取其当前状态；不再校验当前商品能否新建预约 | REQ-017、018 |
| 同买家、同 requestId、不同内容 | 拒绝并独立记录失败日志，不覆盖首次请求记录 | REQ-017、022 |
| 新标识，本人已有有效预约 | 新请求记录关联已有预约，返回已有预约，不新建、不重复业务成功日志和通知 | REQ-017、029 |
| 新标识，预检发现他人占用或商品不可售 | 普通业务校验失败；不泄露他人预约编号或联系方式 | REQ-011、018、030 |
| 新标识，预检发现版本或价格已变化 | 拒绝，提示刷新核对；新动作使用新标识，不能静默按新价预约 | REQ-011、018 |
| 预检通过，锁定后发现状态、版本、价格或有效预约变化 | 明确归为并发竞争；本人另一请求已成功则返回已有预约，否则返回竞争失败 | REQ-006、016、017、018 |
| 正常成功 | 同事务保存预约与快照、商品已预约、首次请求结果、成功日志及待发送通知 | REQ-011、015、020、022 |
| 数据库写入失败 | 整体回滚，不能返回成功；失败留痕，不归类为普通竞争 | REQ-020、022、026 |
| 提交确认丢失或网络超时 | 返回结果待核对；原 requestId、原内容重试，不贸然认定失败 | REQ-011、017、026 |
| 通知投递失败 | 提交后重试通知，不回滚交易、不重复建预约 | REQ-020 |

## 初稿设计选择

- **请求指纹**覆盖 productId、expectedVersion、expectedPrice，先做确定的规范化；buyerId 从会话取得，唯一键为 `(buyerId, requestId)`。指纹的字段选择属于实现推断，必须可靠区分请求内容，不能依赖未经校验的客户端指纹。（REQ-002、017）
- **同键请求事务级互斥**是逻辑锁能力，不假设已存在一行可供 `SELECT FOR UPDATE`。实现可选数据库事务级 advisory lock 或等价机制，并保留请求键唯一约束；仅先查再插无法解决同键并发。锁在读取首次结果前取得，事务结束释放，不新增 ReservationRequest 的“处理中”枚举或已提交占位记录。（REQ-017、029）
- **新请求分支优先级**为归属/可访问性 → 本人已有有效预约 → 他人占用/不可售 → 版本/价格变化。本人已有预约优先返回它，避免新标识重试误报状态错误；同旧标识的重放更早处理。（REQ-011、017、018）
- **商品行锁＋锁后重读**为本稿并发策略，隔离级别选择 READ COMMITTED。预检仅用于判断与友好反馈，不代替锁后验证。所有可能改商品或关联有效预约的写操作都须先锁商品行，并按一致顺序取锁；配合数据库的有效预约唯一约束。此图未为其他用例自动完成该锁协议，实现时仍须落实。（REQ-006、015、016、020、029）
- **失败类型按检测阶段区分**：预检已观察到的失效是普通校验失败；预检通过后复核发现变化是并发竞争失败。这是初稿的分类约定，不声称能证明请求发出前后所有真实时间顺序。锁等待/死锁/数据库故障属于技术异常，不可伪报为已被预约。（REQ-016、018、024）
- **业务拒绝也保存首次结果**，与失败日志一起提交，但不写成功日志、待发送通知或新预约。该结果持久性让后续原标识重试可重放；若保存结果或提交失败，则按系统异常收尾，不能声称已有可重放结果。系统回滚后原键可重新处理。（REQ-017、020、022）
- **整段写入集中异常收尾**：任一必要写入抛错立即跳过后续写入；COMMIT 失败若明确回滚则全撤销，若无法确认则走结果未知。数据库约束异常在本图锁协议下视为需要回滚和核查的技术异常，不直接视为普通竞争成功返回。（REQ-020、026）
- **通知从已提交数据库记录恢复**，不只依赖进程内提交回调。按事件键和接收人去重，投递状态更新失败也可安全重试。通知投递不阻塞用户成功响应；图中将它放在响应之后，表达一种合法执行顺序。（REQ-020）

## 与现有模型的一致性

- 使用现有 ReservationRequest 的 requestId、requestFingerprint、resultCode、resultReason，以及关联 User / Reservation 的关系；“校验失败、并发竞争失败、已有预约”是请求结果分类，不是 ProductStatus / ReservationStatus 新状态。
- 事件沿用“买家提交预约”；成功时商品 `已发布 → 已预约`，预约创建为 `待卖家确认`。
- 有效预约仅为 `待卖家确认`、`已确认`；历史终态预约不删除、不复活。重放成功不表示预约现在仍有效，须并列显示原结果与查询时的当前状态。
- `expiresAt = createdAt + 24小时` 沿用 REQ-013 和现有预约状态图；其精确边界的来源保留原需求中的待真实核对说明。
- 未修改现有类图、状态图或组件图。

```bash
java -DPLANTUML_LIMIT_SIZE=12000 -Djava.awt.headless=true \
  -jar ~/tools/plantuml/plantuml.jar -charset UTF-8 -tpng UML/提交预约序列图.puml
```

此图分支较多，PNG 为完整长图。默认4096像素高度会裁切，重新生成时须保留上述上限设置。已分段检查中文、分支边框、底部图例和通知路径；报告中不宜把整图强缩到单页，可按“幂等处理／新请求校验／事务及通知”分段排版。
